InputOTP takes a pasted code whole. A paste, a one-time-code autofill or a keyboard's clipboard suggestion that carries a whole code (at least `length` code characters) now becomes the code, however much of one the field already holds. Before, the field added it to the end of whatever had been typed and cut the result at the last cell, so "12" followed by a pasted "482913" gave 124829, and a paste on a full code changed nothing, which on an iPhone (where the field keeps no selection to paste over) left no way to paste a new code over an old one. Anything shorter than a whole code still lands where typing would, in the first unfilled cell, and is cut at the last cell, so typing, deleting and a code pasted in parts (Gboard offers "482 913" as two suggestions, "482" and "913") behave as before. That now holds even when the platform's caret was left inside the code: part of a code pasted there used to land in the middle of it, and a character deleted there now comes off the end, as a delete at the end would. A fill that sets the whole text (Android's autofill, a browser's password manager) becomes the code. On an iPhone and on Android a code pasted before the first cell also lands whole, and an edit that follows a paste within a frame or two (a keystroke right after it) lands on the pasted code instead of mixing it with the text the field had before. In a one-cell field every character is a whole code, so typing there now replaces the character instead of being refused. When pasted text holds more than one code's worth of characters, the first `length` of them become the code.

An `alphanumeric` code now keeps only ASCII letters and digits, as a numeric code keeps only digits: spaces, dashes and other separators no longer take a cell, so a pasted "AB-12 CD" fills AB12CD instead of "AB-12 ".
